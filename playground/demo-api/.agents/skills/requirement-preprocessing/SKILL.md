# PRD 预处理工具

## 概述

对产品需求文档进行预处理的工具,核心功能包括需求复杂度评估与拆分、接口信息整合。输出符合 `references/prd-template.md` 模版结构的规范化 PRD 文档。

## 何时使用

**使用场景**:

- 用户提供原始 PRD 或产品需求文档
- 需求描述过于复杂,需要拆分成多个迭代
- 需要将后端接口信息整合到需求文档中
- 用户明确说"帮我预处理 PRD"或"整理需求文档"

**不使用场景**:

- 用户已提供完全符合模版的规范化 PRD 文档
- 用户明确表示不需要任何预处理
- 仅需要查看 PRD 模版格式(直接提供模版即可)

## 快速参考

### 处理流程概览

| 步骤                | 输入                   | 输出                           | 跳过条件           |
| ------------------- | ---------------------- | ------------------------------ | ------------------ |
| 1. 复杂度评估与拆分 | 原始需求文档           | 拆分后的多期文档或原文档       | 用户明确说不拆分   |
| 2. 接口信息整合     | 接口 ID 列表或需求描述 | 包含接口详情或 Mock 定义的文档 | 用户明确跳过此步骤 |
| 3. 输出文档         | 处理后内容             | 规范化 PRD 文档                | -                  |

## 处理流程

### 第一步:需求复杂度评估与拆分

**触发条件**:默认执行,除非用户明确说明"不做拆分"或"不需要拆分"。

**评估标准**:

| 维度           | 阈值              | 说明         |
| -------------- | ----------------- | ------------ |
| 功能点数量     | ≥ 5 个 P0/P1 功能 | 核心功能过多 |
| 业务模块       | ≥ 3 个模块/页面   | 涉及范围广   |
| 接口数量       | ≥ 8 个接口        | 后端工作量大 |
| 业务流程复杂度 | 多审批流/复杂计算 | 逻辑复杂     |
| 预计工作量     | > 2 周            | 开发周期长   |

满足任一条件即建议拆分。

**拆分原则**:

1. **按业务功能拆分**:将相关功能组合为一个迭代
2. **按页面拆分**:如果涉及多个独立页面,可按页面拆分
3. **按优先级拆分**:P0 功能优先,P1/P2 功能后续迭代
4. **依赖关系考虑**:有强依赖的功能应放在同一迭代或前后迭代
5. **工作量均衡**:每个迭代的工作量应相对均衡(1-2周为宜)

**拆分后文档要求**:

- 每个文档保持完整的 PRD 结构(按 prd-template.md)
- 在需求概述中说明本期迭代的范围和与其他期的关系
- 功能列表只包含本期需要实现的功能
- 接口文档只包含本期需要的接口

### 第二步:接口信息整合

**两种模式**:

#### 模式 1:后端接口已开发(集成真实接口)

**检查接口编号**:

1. 检查需求文档中是否提供了相关接口编号
   - 格式示例:"相关接口编号:xxxx、xxxxx"或"接口编号:xxxx"
2. 如果没有提供:询问用户"是否有相关的后端接口编号?如果有,请提供接口编号(多个接口用逗号分隔)"
3. 如果用户提供接口 ID:进入**真实接口集成流程**

**真实接口集成流程**:

1. **识别接口 ID**:从用户输入中提取接口 ID 列表
2. **调用 api-info skill**:
   - 为每个接口 ID 调用 api-info skill
   - 获取接口的详细信息(不做文件输出,仅获取内容)
3. **整合接口信息**:
   - 如果做了需求拆分,根据功能归属将接口信息补充到对应的迭代文档中
   - 如果未拆分,直接补充到原需求文档中
   - 接口信息补充到文档的"接口文档"章节

#### 模式 2:后端接口未开发(定义 Mock 接口)

**触发条件**:用户回复"没有"或"暂无"接口编号时,自动进入 Mock 接口定义模式。

**Mock 接口定义流程**:

1. **分析需求中的功能点**:识别每个功能需要的接口操作(查询、新增、编辑、删除等)
2. **定义 Mock 接口规范**:
   - 接口命名:遵循 RESTful 风格或项目约定
   - 请求方式:根据操作类型确定(GET/POST/PUT/DELETE)
   - 请求参数:基于功能需求定义必要参数
   - 响应格式:定义标准响应结构和字段
   - TypeScript 类型:为请求和响应定义 TS 类型接口
3. **整合到文档**:
   - 在"接口文档"章节标注"【Mock 接口定义】"
   - 提供完整的接口规范,方便前端 Mock 开发
   - 同时作为后端接口开发的参考文档

**接口文档格式**:

```markdown
## 四、接口文档

### 4.1 接口列表

| 接口编号 | 接口名称     | 请求方式 | 说明         | 状态        |
| -------- | ------------ | -------- | ------------ | ----------- |
| API-001  | 【接口名称】 | GET/POST | 【接口说明】 | Mock/已开发 |
| API-002  | 【接口名称】 | GET/POST | 【接口说明】 | Mock/已开发 |

### 4.2 接口详细说明

#### API-001 【接口名称】【Mock 接口定义】

【从 api-info skill 生成的详细接口信息或者mock,包括请求参数、响应格式、TypeScript 类型定义等】
```

### 第三步:输出文档

**输出路径规则**:

- **需要拆分的情况**:创建多个需求文档

```

./developer/{版本日期}/{需求名称}/【需求名称】-第一期.md
./developer/{版本日期}/{需求名称}/【需求名称】-第二期.md
./developer/{版本日期}/{需求名称}/【需求名称】-第三期.md
...

```

示例:`./developer/2024-01-15/user-management/user-management-第一期.md`

- **不需要拆分的情况**:单个文档

```

./developer/{版本日期}/{需求名称}/{需求名称}.md

```

示例:`./developer/2024-01-15/user-management/user-management.md`

**版本日期规则**:

- 优先使用用户提供的日期
- 如果未提供,使用当前日期(YYYY-MM-DD 格式)

## 使用示例

### 示例 1:简单需求,无接口整合

**用户输入**:

```

帮我预处理这个PRD #doc

```

**处理流程**:

1. 评估复杂度 → 判断为简单需求(< 5 功能点)
2. 跳过拆分
3. 检查没有接口编号，进入 Mock 接口定义模式 → 根据功能需求定义接口规范
4. 输出:`./developer/2025-01-27/simple-feature/simple-feature.md` (包含 Mock 接口定义)

### 示例 2:复杂需求,需要拆分,定义 Mock 接口

**用户输入**:

```

这是一个用户管理系统的PRD #doc
包含:用户列表、用户详情、角色管理、权限管理、审批流、日志管理等6个模块

```

**处理流程**:

1. 评估复杂度 → 涉及 6 个模块,建议拆分
2. 拆分为 3 期:
   - 第一期:用户列表 + 用户详情
   - 第二期:角色管理 + 权限管理
   - 第三期:审批流 + 日志管理
3. 询问接口编号 → 用户回复"暂无"
4. 为每期定义对应的 Mock 接口
5. 输出:
   - `./developer/2025-01-27/user-management/user-management-第一期.md`
   - `./developer/2025-01-27/user-management/user-management-第二期.md`
   - `./developer/2025-01-27/user-management/user-management-第三期.md`

### 示例 3:带真实接口信息整合

**用户输入**:

```

帮我预处理这个PRD #doc
接口IDs: 882108、598585、598578

```

**处理流程**:

1. 评估复杂度 → 判断是否需要拆分
2. 检测到接口 ID → 进入真实接口集成模式
3. 调用 api-info skill 获取 3 个接口的详细信息
4. 将接口信息整合到文档的"接口文档"章节
5. 输出包含完整接口信息的 PRD 文档

## 常见错误

### 错误 1:强制拆分简单需求

**问题**:不管需求复杂度如何,都进行拆分

**修复**:严格按照拆分判断标准评估,简单需求不拆分

### 错误 2:接口归属不清晰

**问题**:拆分后的文档中,接口信息没有正确归属到对应的功能

**修复**:根据接口的用途,将其归属到使用该接口的功能所在的迭代文档中

### 错误 3:拆分后文档结构不完整

**问题**:拆分后的某个文档缺少必要章节(如接口文档、测试要点)

**修复**:每个拆分后的文档都必须保持完整的 PRD 结构,参照 prd-template.md

### 错误 4:版本日期格式不统一

**问题**:使用不同的日期格式(2024/01/15、2024-1-15)

**修复**:统一使用 YYYY-MM-DD 格式(如 2024-01-15)

### 错误 5:Mock 接口定义不完整

**问题**:Mock 接口缺少请求参数、响应格式或 TypeScript 类型定义

**修复**:Mock 接口定义必须包含完整的接口规范,包括请求参数、响应格式、TS 类型、Mock 数据示例,确保前端可以直接用于开发

### 错误 6:未区分 Mock 和真实接口

**问题**:文档中没有标注接口是 Mock 定义还是已开发的真实接口

**修复**:在接口列表中增加"状态"列,在接口详细说明中标注【Mock 接口定义】或接口来源

## 注意事项

1. **拆分合理性**:拆分时要考虑功能的完整性和依赖关系,避免将强依赖的功能分到不同期
2. **接口归属清晰**:接口信息要准确归属到对应的功能和迭代
3. **文档格式规范**:输出的文档必须严格符合 `references/prd-template.md` 模板格式
4. **命名清晰**:文件命名要清晰表达内容和期数,使用中文"第一期"而非"phase1"
5. **模版理解**:熟悉 prd-template.md 的各章节用途(需求概述、功能需求、非功能需求、接口文档、数据字典、测试要点)
6. **Mock 接口规范**:Mock 接口定义要完整、规范,既能支持前端 Mock 开发,也能作为后端开发的接口文档参考
7. **接口状态标注**:清晰标注接口是 Mock 定义还是真实接口,避免混淆

## 技能依赖

- **api-info** skill - 用于获取真实接口详情,如果该 skill 不可用,提示用户:"建议安装 api-info skill 以获取接口详细信息"
