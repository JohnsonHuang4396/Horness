# Code Review Skill

## V3 执行证据边界

- 禁止用规则文件存在代替本次执行证据；必须记录本次实际读取的变更、检查清单和验证命令。

AI 代码审查工具，确保 AI 生成的前端代码"能上线、可维护"，建立可信任交付过程。

## 核心功能

1. **自动确定审查范围**：智能获取变更文件或指定分支对比
2. **全面质量检查**：按照项目规范进行规范、逻辑、性能、安全等维度全面审查
3. **详细问题定位**：提供问题代码、修复建议和修复原因
4. **标准化报告输出**：生成结构化的审查报告

## 审查原则

1. **历史代码豁免**：仅审查新增和修改的代码，历史代码不纳入审查范围
2. **新增代码严格**：所有新增/修改代码必须 100% 遵守规范
3. **分级审查**：明确标注问题级别（P0/P1/P2），便于优先级排序
4. **具体可操作**：每个问题都要提供具体的修复代码和修复原因
5. **引用规范**：每个问题都要引用对应的规范文档位置
6. **开发阶段数据豁免**：以下情形属于开发阶段的合理占位，**不判定为问题，不纳入任何级别缺陷统计**：
    - mock 数据、临时占位字符串（如 `'TODO_REPLACE_WITH_REAL_REPORT_CODE'`、`'PLACEHOLDER'`、`'mock_xxx'` 等）
    - 开发阶段尚未由后端提供的 reportCode、接口 URL、枚举值等配置项
    - 注释中明确标注 `TODO` / `FIXME` / `待补充` / `暂不实现` / `待联调` 的占位逻辑
    - 函数体为空实现或以 `throw new Error('not implemented')` 等方式占位，且有注释或命名能表达「待后续实现」
    - 被注释掉的整段代码块，且注释中注明了暂不启用的原因或待补充说明
    - **判定依据**：变量/字符串的命名或注释能明确表达「当前为临时值/待实现/暂不启用」即可豁免，不追究其逻辑完整性、类型覆盖或代码质量

## 审查流程

> **强制约定**：步骤 1 → 2 → 3 → 4 →
> 5 必须完整顺序执行，**不得在任意步骤完成后停下来等待用户指令或提前向用户输出结果**。唯一允许中途停止的情况：用户主动要求中止。

### 步骤 1：确定代码审查范围

**场景 A：用户未明确指定范围**

直接获取当前 Git 工作区的变更文件作为审查范围：

```bash
# 使用 scripts/get_git_diff.sh 获取工作区变更
./scripts/get_git_diff.sh
```

脚本会自动获取：

- **已暂存的变更**（git add 后的文件）
- **已修改未暂存的变更**（修改但未 git add 的文件）
- **未跟踪的新文件**（新创建但未 git add 的文件）
- 输出详细的代码差异（仅前端相关文件：.ts、.vue、.js、.scss、.css 等）

**使用场景**：

- 开发任务完成后，准备提交前的代码审查
- 对当前正在修改的代码进行即时审查
- 确保代码符合规范后再 commit

**场景 B：用户明确指定分支对比**

当用户说明了要对比的分支时：

```bash
# 对比指定分支
./scripts/get_git_diff.sh <base_branch> <target_branch>

# 示例
./scripts/get_git_diff.sh main feature/order-management
```

**使用场景**：

- 需要审查某个功能分支相对于主分支的所有变更
- 代码已提交，需要在合并前进行审查

**场景 C：用户指定具体文件**

直接读取用户指定的文件内容进行审查。

**使用场景**：

- 用户明确指出要审查的具体文件
- 需要重点审查某个关键文件

**重要提示**：

- 获取变更范围后，必须读取所有变更文件的完整内容
- 不要仅依赖 diff 输出，要读取完整文件以全面理解代码上下文
- 对于大型变更（超过 20 个文件），可以先列出文件清单，让用户确认审查范围

### 步骤 2：加载审查标准

在开始审查前，**必须按顺序读取全部三份清单**，不得跳过任何一份：

```bash
read_file references/check-standard.md   # 规范符合性 + 逻辑正确性
read_file references/check-quality.md    # 架构设计 + 性能 + 可维护性
read_file references/check-security.md   # 安全性
```

**三份清单覆盖的检查域**：

| 清单文件            | 覆盖范围                                                                     | 关键 P0 项举例                                                   |
| ------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `check-standard.md` | 目录结构、文件命名、代码命名、CSS BEM、导入规范、TypeScript 约束、路由、API  | 路由禁用 params、CSS 必须 BEM、禁止 any、JSON.parse 须 try-catch |
| `check-quality.md`  | 分层架构、模块职责、组件化、渲染性能、内存泄漏、可维护性、请求优化、资源加载 | 禁止跨层调用、v-for 禁用 index 作 key、定时器须清理              |
| `check-security.md` | XSS 防护、敏感数据、CSRF、路由权限、依赖安全、接口安全、点击劫持             | 禁止 v-html 渲染用户输入、Token 不得明文存储、路由权限不得误关   |

**优先级约定**（贯穿全程）：

- **P0**：必须修复，阻塞上线
- **P1**：必须修复，阻塞上线
- **P2**：建议优化，可后续处理

### 步骤 3：执行代码审查

**按三份清单逐域检查**

严格按照步骤 2 加载的三份清单逐域审查，**不允许跳过任何清单的检查项**。

**审查执行顺序**：

```
check-standard.md → check-quality.md → check-security.md
```

**每个问题必须记录以下字段**：

| 字段     | 说明                                             |
| -------- | ------------------------------------------------ |
| 问题编号 | 格式：`【P0-01】`、`【P1-01】`，按优先级分组递增 |
| 所属清单 | 来自哪份 check-\*.md（标准 / 质量 / 安全）       |
| 问题描述 | 清晰描述违反了哪条规范                           |
| 问题位置 | 文件路径 + 行号                                  |
| 问题代码 | 用 ❌ 标记                                       |
| 建议修复 | 用 ✅ 标记，给出可直接使用的修复代码             |
| 规范引用 | 引用对应 check-\*.md 中的章节编号                |

**各清单重点提示**：

> check-standard.md — 规范与逻辑

- P0 强查：CSS BEM、路由禁用 params、JSON.parse 须 try-catch、禁止页面直调 API
- P1 关注：导入顺序、配置抽离到 useConfig.ts、响应式数据正确使用

> check-quality.md — 架构与质量

- P0 强查：禁止跨层调用（页面→Service→API→HTTP）、v-for
  key 禁用 index、大列表必须虚拟滚动、定时器/监听器/第三方实例须在 onUnmounted 清理
- P1 关注：组件 props ≤ 10 个、配置数据抽离、函数 ≤ 50 行、模板禁止直接调用函数、路由组件懒加载、搜索防抖

> check-security.md — 安全

- P0 强查：v-html 必须经 DOMPurify 过滤、Token 不得明文存 localStorage、路由 requiresSignIn / requiresAuth 不得误关
- P1 关注：CSRF Token 不得绕过系统 HTTP 封装、接口密钥不得硬编码

### 步骤 4：打包构建验证

**跳过条件**：项目根目录不存在 `package.json` 或 `package.json` 中不含 `build` 脚本时跳过，并在审查报告中注明原因。

```bash
pnpm build
```

**说明**：

- 验证整个项目能否完整编译打包，覆盖 TypeScript 编译错误、模块依赖缺失、内存溢出等运行时构建问题
- 构建成功：命令退出码为 0，控制台无 Error 输出
- 构建失败：收集完整错误信息（错误类型 + 文件路径 + 错误描述），作为 **P0 问题** 记入审查报告

**失败处理**：构建失败视为 P0 问题，阻塞上线，在步骤 5 报告中单独列出 `【P0-BUILD】` 问题项。

### 步骤 5：生成审查报告

**5.1 读取报告模版**

严格按照模版结构填写审查报告

```bash
read_file references/code-review-report-template.md
```

**5.2 确定报告输出位置**

**默认输出路径**（用户未明确指定时）：

```
.agents/changes/specs/{YYYYMMDD}/{需求名称}/coding/review/code_review_v{N}.md
```

当前上下文没有创建变更目录 时，在 .agents/changes/specs/ 下创建变更目录：{YYYYMMDD}/{需求名称}/

**用户自定义输出**：如果用户明确指定了输出路径，则使用用户指定的路径。

## 常见问题处理

### 变更文件过多

如果变更文件超过 20 个，建议：

1. 先列出文件清单，让用户确认审查范围
2. 按模块分批审查（如先审查 API 层，再审查页面层）
3. 优先审查核心业务文件

### 无法确定分支

如果 Git 命令执行失败：

1. 提示用户当前不在 Git 仓库中
2. 请用户手动指定要审查的文件路径
3. 或者让用户提供代码内容进行审查

### 评分标准

代码质量评分参考：

- 90-100 分：优秀，可直接上线
- 80-89 分：良好，修复所有 P0/P1 问题后上线
- 70-79 分：一般，P0/P1 问题较多，修复后上线
- 60-69 分：较差，需要大量修复
- <60 分：差，建议重构
