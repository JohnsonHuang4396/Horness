# DevOps 与发布工程实践

## 适用时机

- 在 Docker、Kubernetes、Terraform、Helm、CI/CD 和部署项目中维护构建、发布、健康检查、秘密和回滚。
- 只在当前项目证据和任务目标同时命中时加载；不因为目录、历史任务或来源项目名称自动触发。

## 进入前检查

- 读取项目根目录和模块边界，确认该技术栈真实存在，不凭目录或用户猜测激活。
- 读取 resources/stack-packs/devops-engineering.md 的通用检查清单和项目内同类实现。
- 核对业务项目声明的运行时版本、构建命令、测试命令、环境变量键名和部署入口。

## 执行流程

1. 先写任务目标、允许范围、当前阶段、Assurance 模式和退出条件；把用户原话、仓库事实、推断和未知项分开。
2. 建立本 Skill 的输入清单和证据索引；每项证据记录路径/命令、时间、哈希或版本，敏感内容只保留键名和脱敏指纹。
3. 依次执行以下专项检查：
   - 先读取项目声明的运行时、构建描述、锁文件、模块入口和已有验证脚本；不能因为 Harness Node 版本而升级业务项目。
   - 将该技术栈的调用链、版本、配置、依赖、测试、部署和兼容边界写入影响账本。
   - 优先复用项目已有框架、插件、访问层和发布流程；跨边界变化需要设计和批准。
   - 将关键技术事实和详细检查放在本 Skill 的 references/stack-pack.md，正文只保留执行入口和门禁。
4. 复核直接消费者、间接消费者、配置/资源/脚本/测试/部署路径，发现新影响立即暂停并更新影响账本。
5. 只生成当前阶段允许的文件和结构化产物；不把候选事实、设计建议或模型推断写进正式规则。
6. 选择与项目版本匹配的最窄验证，再按风险扩大；记录命令、工作目录、版本、退出码、时长、输出路径和未运行项。
7. 输出中文摘要：已读取、已决定、实际修改/产出、验证证据、未知项、风险、回退和下一步。

## 输出物

- 技术栈工程报告
- 版本/依赖/调用链/验证矩阵
- 兼容、发布和回滚记录

## 质量门禁

- 技术栈 Skill 只在项目证据和当前任务同时命中时使用。
- 旧运行时、锁文件、公共 API、数据库/消息/部署契约没有被无批准改变。
- 验证结果包含真实命令、退出码、版本和未运行项，不能把静态阅读当通过。
- Skill 删除后 Core Harness 和项目基本流程仍能运行。

## 失败与回退

- 输入或目标不清：回到需求确认阶段，列出最少的待确认问题。
- 发现新影响：暂停当前批次，更新影响账本和计划后再继续。
- 工具或环境失败：记录原始输出，区分可重试、需修复和需人工处理。
- 安全、契约或数据一致性失败：阻断交付，不用文字摘要掩盖。

## 明确边界

- 不把模型猜测、目录名或旧摘要当作权威事实。
- 不越过当前阶段职责，不顺手修改无关文件。
- 不读取或输出秘密，不执行未批准的高风险外部动作。

## 最小示例

- 以一个真实的小任务为例，展示输入事实、关键决定、产出文件和验证结果。
- 正向触发：用户任务明确命中本 Skill 的职责，且项目证据可以支撑执行。
- 负向触发：只有相似关键词、没有项目证据、或任务属于另一个阶段时，记录排除原因并不加载本 Skill。
